# Solution 2 — ACXD DEV → GitHub → Harness → ACXD QA

## Architecture

Three distinct Amazon Connect instances/workspaces exist, but only DEV and QA participate in this pipeline. A DEV operator exports selected ACXD application/flow definitions with an API key, commits the JSON to a private GitHub repository, then triggers Harness with the exact commit SHA. Harness checks out that commit, validates checksums, applies explicit QA substitutions, and updates/builds/deploys the matching ACXD applications in the QA workspace.

## Contents

- `scripts/acxd.mjs`: DEV export, offline bundle validation, mapped QA upsert/build/deploy.
- `scripts/export-to-github.sh`: clones, exports, validates and commits DEV JSON to GitHub.
- `scripts/harness-qa.sh`: local equivalent of Harness execution.
- `harness-pipeline.yaml`: Harness Custom stage and delegate ShellScript.
- `config/applications.json`: select application names.
- `config/qa.mapping.example.json`: replacement and dependency review policy template.
- `apps/`: JSON definitions generated by `export`.

## Prerequisites

1. Private GitHub repo with branch protection and approvals. Add this package (including a committed `package-lock.json` generated with `npm install` in a network-connected environment) to the repo.
2. Node.js >=20, Git, network access to the SDK, and an SSH deploy key with GitHub read access on the Harness Delegate. The DEV export bot needs a distinct *write* deploy key.
3. Set ACXD_REGION for each workspace if the SDK needs explicit region selection. DEV ACXD API key read/list permissions; QA ACXD API key list/get/create/update/build/deploy permissions; correct workspace UUID for each.
4. Harness project, delegate tagged `acxd-release`, secrets `acxd_qa_api_key` and `acxd_qa_mapping_json`. QA mapping secret must be JSON text, based on `config/qa.mapping.example.json` with real values and no placeholders.
5. Review permissions and external dependencies (Lambda, Connect queues, KB, guardrails, data requests, slot types, context variables, integration endpoints) before live deployment.

## DEV export

```bash
export ACXD_API_KEY='DEV_KEY'
export ACXD_WORKSPACE_ID='DEV_WORKSPACE_UUID'
export GITHUB_REPO_SSH='git@github.com:ORG/acxd-definitions.git'
export GIT_SSH_COMMAND='ssh -i /secure/path/dev-export-write-key -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes'
# Configure GitHub in known_hosts first; DO NOT disable host key verification.
bash scripts/export-to-github.sh
```

Configure `config/applications.json` before the export. The export recreates only `apps/`, and generates deterministic numbered files and a checksum manifest. Push the code initially (including a real lockfile) before running export.

## Harness run

1. Commit the generated `apps/` to GitHub.
2. Copy `harness-pipeline.yaml` into Harness; replace placeholders.
3. Set `acxd_qa_mapping_json` to your reviewed JSON mapping.
4. Harness delegate must have a *read-only* SSH key to GitHub, set via its SSH agent or secure Git configuration; do not embed key material into YAML.
5. Run the pipeline and supply the FULL Git commit SHA of the exported JSON.
6. Watch logs for checksum verification, dry run, flow sync, app sync, build status and deployment status.
7. Perform real QA conversation/integration tests afterwards; these are not included in this minimal implementation.

## Processing and safety

- Exported source workspace/application IDs and server-generated fields are **not** replayed to QA.
- Flows (including default and lifecycle hook flows) are created/updated by logical `flowId` first.
- Application records are created by name or updated by explicit target application ID.
- JSON substitutions apply only to *values*, never JSON property names.
- Source reference deny-list and selected external dependency field scanning can block promotion.
- QA one-click deployment is disabled; a new build is created and checked before deployment.
- Idempotence is limited: another run creates a new build. Coordinate executions and maintain recovery snapshots.

## Known limitations / release blockers

- SDK documentation does not provide a single complete export/import endpoint. This package covers applications and attached/default/lifecycle flows, not all workspace resources.
- Dependency scanning is incomplete for arbitrary custom node payloads. Before production use, examine the exported JSON and extend schema-specific checking; `approvedExternalDependencies` accepts exact `property.path=value` strings only.
- Applications may use guardrails, KBs, slot types, context variables, data requests, languages, voice configuration, or connections that need separate provisioning and ID maps.
- No real smoke tests, automatic rollback, drift detection, artifact signing, comprehensive snapshots, or execution locking. These must be added for a production-grade gate.
- For production deployment, rework code to capture previous deployment state, protect shared flows and control concurrent promotions.
- SDK dependency is pinned to 0.2.0 based on the available package index; create and commit package-lock.json using npm install with network access, then future runs use npm ci.
- Validate against disposable QA workspace resources first and confirm compatibility of specific response shapes/status values with the installed SDK.
